## Project

Staff admin dashboard for White Castle Motel (Eldoret). Next.js 16 App Router, React 19, TypeScript (strict), Tailwind CSS v4, shadcn/ui (`radix-vega` style, `radix-ui` package). No backend exists yet — auth and data are mocked in-app.

## Next.js version warning

This is **Next.js 16**, which has breaking changes from earlier versions (see [AGENTS.md](AGENTS.md)). Before writing framework-facing code (routing, caching, data fetching, proxy/middleware, metadata), read the relevant guide under `node_modules/next/dist/docs/01-app/` rather than relying on prior knowledge.

## Architecture

### Route groups

- `app/(auth)/` — public screens: `/login`, `/forgot-password`, `/reset-password`, plus `/change-password` (authenticated, not public: the forced new-password screen for accounts flagged `must_change_password`). Its layout renders the branded split panel (gradient aside + centered form column). Pages are thin: they set `metadata.title` and compose `AuthPanel` + a form component.
- `app/(dashboard)/` — authenticated area: `/dashboard`, `/bookings`, `/guests`, `/units`, `/requests`, `/reports`, `/users`, `/settings`, `/profile`. Most pages are stubs; `/profile` renders `components/profile/profile-view.tsx` (account details, change-password dialog, sign out).
- `app/page.tsx` redirects `/` → `/login`.
- `app/layout.tsx` is the root: loads fonts (Inter → `--font-sans`, Manrope → `--font-heading`, IBM Plex Sans → `--font-ibm-plex`, Geist Mono → `--font-mono`) and wraps everything in `ThemeProvider` (next-themes, class strategy) → `AuthProvider` → `TooltipProvider`.

### Auth

The backend is a FastAPI-style API (errors come back as `{ detail: string | ValidationError[] }`; use `getApiErrorMessage` from `lib/api/errors.ts`).

- **The browser never calls the backend origin directly.** `next.config.ts` rewrites `/api/:path*` to `API_PROXY_TARGET` (server-only env), and `NEXT_PUBLIC_API_BASE` is `/api`. This keeps the refresh cookie same-site: the backend sets it `SameSite=Lax` without `Secure`, so a cross-site call from `localhost` would never store or send it and every reload would land on `/login`. See `.env.example`. Restart `npm run dev` after editing `.env`.

- **Token model:** the access token lives only in memory (`lib/auth-token.ts`); the refresh token is an HTTP-only cookie set by the server. Nothing auth-related is written to localStorage.
- `lib/axios.ts` exports `axiosInstance` (baseURL + `withCredentials`). Its request interceptor injects `Authorization: Bearer`, and its response interceptor refreshes once on a 401 (`POST /auth/refresh`, deduped across concurrent failures) and replays the request. If the refresh fails it fires `onUnauthorized` listeners. Use this instance for every authenticated call.
- `lib/api/auth.ts` wraps the auth endpoints. `login`, `requestPasswordReset` (`/auth/password-reset`), and `confirmPasswordReset` (`/auth/password-reset/confirm`) use bare `axios` so interceptors never touch them; `fetchMe` (`/auth/me`), `logout`, and `changePassword` (`PATCH /auth/change-password`) use `axiosInstance`.
- `providers/auth-provider.tsx` exposes `useAuth()` (`user`, `accessToken`, `status`, `isLoggedIn`, `login`, `logout`, `refreshUser`). On mount it refreshes, fetches `/auth/me`, then routes: signed-in visitors on `/` or a public auth route go to `/dashboard`; failures on a protected route go to `/login`. While that runs it renders `WorkspaceLoader` instead of the app. `isPublicRoute()` is the single source of truth for public paths.
- `components/auth/require-auth.tsx` wraps the `(dashboard)` layout and bounces unauthenticated users to `/login`, and users with `must_change_password` to `/change-password`.
- **Temporary passwords.** `getLandingPath(user)` (in the provider) returns `/change-password` when `must_change_password` is true, else `/dashboard`; the login form, the bootstrap redirect and `RequireAuth` all use it so a reload cannot skip the step. `components/auth/forced-change-password-form.tsx` calls the same `changePassword` endpoint as the profile dialog, then `refreshUser()` (re-fetches `/auth/me`) and routes to the dashboard. The three password inputs are shared via `components/auth/change-password-fields.tsx`.
- Two account menus share one popover pattern: `components/dashboard/sidebar-user.tsx` (sidebar footer, name + role, gradient popover) and `components/dashboard/header-user.tsx` (header, name + email, porcelain popover, avatar-only under `sm`). Both use the `useLogout()` hook (`hooks/use-logout.ts`) and `getInitials()` from `lib/format.ts`; reuse those rather than re-implementing sign-out or initials.
- **Server state: always `@tanstack/react-query` + `axiosInstance`.** Never call `axios`/`fetch` directly from a component. API helpers live in `lib/api/*` (one file per resource, each exporting `fetch*`, `create*` where the resource is writable, and a `*QueryKey`). Reads use `useQuery` with that key (gate with `enabled` when the data is only needed inside a dialog). Mutations use `useMutation` inside the component, invalidate the resource's query key on success, show a `toast.success`, and surface failures via `setError("root", …)`. See `components/users/create-user-dialog.tsx` (adds a `useQuery`-fed shadcn `Select` via `Controller`, and a generated temporary password from `lib/password.ts` that always satisfies `passwordSchema`; `must_change_password` is hard-coded `true` in `toCreateUserPayload`). Tables: `components/users/users-table.tsx` and `roles-table.tsx` are `useQuery`-backed with client-side search (`SearchInput` in `table-toolbar.tsx`); loading/empty/error rows come from `table-state.tsx`. The users table resolves role slugs to labels via the roles query (`humanizeSlug` fallback). It lists `GET /auth/users?role=` under `usersListQueryKey(filters)` (`["users","list",{role}]`, prefixed by `usersQueryKey` so existing invalidations still refresh it, `keepPreviousData` dims the old rows while a role loads); the role `Select` beside the search uses an `all` sentinel over `ROLE_NAMES`. **Pagination:** tables show at most 10 rows per page (`PAGE_SIZE`). `hooks/use-pagination.ts` pages an already-filtered list client-side (the APIs don't paginate yet) and clamps the page when the list shrinks; call `setPage(1)` in every filter/search change handler. Render `components/table-pagination.tsx` under the table (only once the query succeeded). The users, payments, bookings, guests and units tables use it so far; roll it out to the others the same way. Row actions live in `user-actions-menu.tsx`: a shadcn `DropdownMenu` (enable / disable / unlock / delete, delete is `variant="destructive"` and only rendered for a signed-in `super_admin`) where enable/disable/unlock/delete open the generic `components/confirm-dialog.tsx` and run one `useMutation`; the signed-in user cannot disable or delete themselves, and a non-super-admin cannot disable a `super_admin` (the item is disabled; `isSuperAdmin` in `lib/roles.ts`). Endpoints: `POST /auth/users/{id}/enable`, `POST /auth/users/{id}/disable`, `POST /auth/users/{id}/unlock` (accounts lock after 5 failed sign-ins; the Unlock account item and the red "Locked" label under the name in `users-table.tsx` both key off `user.is_locked`, not `locked_until`, which the backend leaves set after a lock expires. `AuthUser` also carries `failed_login_attempts`), `DELETE /auth/users/{id}`. **Roles are a fixed set defined by the backend**: `ROLE_NAMES` in `lib/roles.ts` (`super_admin`, `admin`, `receptionist`, `finance`, `housekeeping`, `catering`) is the source of the `RoleName` type used by `AuthUser.role`, `Role.name`, `createUserSchema` (`z.enum`), `RequireRole` and nav items; check membership with `hasRole(role, allowed)` / `isRoleName`. Deposits (`payment_type === "deposit"`) also get Complete payment (`complete-payment-dialog.tsx`, mounted only while open): amount, method and reference (`completePaymentSchema` / `toCompletePaymentParams`; the amount is **read-only**, set to `getRemainingBalance(booking, deposit)` — the booking's current `total_amount` from `GET /bookings/{id}` less the deposit — and Save is disabled while it loads or when the booking is already `fully_paid`) → `POST /payments/complete/{booking_ref}` with **no body**; `amount`, `method`, `reference` (omitted for cash) and `recorded_by` (signed-in `user_id`) go in the query string via axios `params` (`completePayment` in `lib/api/payments.ts`). The method `Select` and the cash-aware reference input are shared with the record form as `PaymentMethodField` / `TransactionReferenceField` in `payment-form-fields.tsx`, which also exports `labelClassName` / `inputClassName` / `FieldError`; the cash rule (`hasReferenceUnlessCash` + `referenceRequiredIssue`) is shared by both schemas. The record dialog is only opened from the top-right CTA and always starts empty. Left of it, `export-payments-dialog.tsx` wraps `ExportCsvDialog` for `GET /payments/export/payments` (`exportPayments`): statuses are `PAYMENT_EXPORT_STATUSES` (`unpaid` / `deposit_paid` / `fully_paid` — the booking payment statuses, not a payment record's `pending`/`verified`/`rejected`), each open starts on All statuses (no `status` param) and the current month's dates. The `Payment` shape in `lib/types.ts` matches the live `/payments/list` response; beyond the create payload it carries `currency`, `status`, `evidence_url` / `evidence_filename`, `verified_by` / `verified_at`, `rejection_reason` and timestamps. `PAYMENT_STATUSES` lists only `pending` / `verified` / `rejected` as filter options — an unsupported value would be rejected by the endpoint — while the badge map tints a few extra slugs in case the API grows one.
- **Dashboard** (`/dashboard`): `components/dashboard/dashboard-view.tsx` reads a single report, `GET /motel/reports/dashboard` (`fetchDashboardReport` in `lib/api/reports.ts`, key `["reports","dashboard"]`, typed as `DashboardReport` in `lib/types.ts`). `hooks/use-dashboard-report.ts` wraps the query with `staleTime: 0` (booking/payment mutations elsewhere don't invalidate it); every section calls the hook and TanStack dedupes, so nothing is prop-drilled. There is no date range: the heading is the report's `date`. Sections: `dashboard-stats-cards.tsx` (today's arrivals / departures / pending approvals / pending payments, copy and tones in `TODAY_STAT_CARDS` in `lib/dashboard.ts`), `period-overview.tsx` (this week / this month revenue and bookings with their `from` date, `OVERVIEW_PERIODS`) and `pending-bookings.tsx` ("Needs attention": `details.pending_bookings` newest first, badge = `today.pending_approvals`, with a footer when the list is shorter than the count). The report also returns room counts, housekeeping/maintenance figures and arrival/departure/task/issue lists that aren't typed or rendered. `report-state.tsx` holds the shared `StatCardSkeleton` / `ReportError`.
- **Settings** (`/settings`, super admins only): the page is wrapped in `RequireRole roles={SETTINGS_ROLES}` (`["super_admin"]` in `lib/roles.ts`) and its link is `settingsNav` in `components/dashboard/nav.ts`, rendered in the sidebar **footer** above `SidebarUser` and as a menu item under Profile in `header-user.tsx` (both gated by `canSeeNavItem(settingsNav, role)`; not in `dashboardNav`, but `findNavItem` still includes it for the header title). `components/settings/settings-list.tsx` lists `GET /motel/settings` (`fetchSettings` in `lib/api/settings.ts`, key `["settings"]`, typed `MotelSetting` = key / value / description / updated_at — every value is a string, `""` when unset) split into full-width sections by `groupSettings` (`lib/settings.ts`): Payments, Cancellations, Bed & breakfast, Notifications, Security, then General for unknown keys; `SETTING_CATEGORY` maps each key to its section and its key order is the reading order within a section. **No colour-coding**: section titles are `text-brand-navy dark:text-foreground`, setting labels and values are `text-slate-900 dark:text-foreground`, and secondary text (summaries, descriptions, updated dates) is `text-muted-foreground`; each section header is a neutral `bg-muted/40` band with a navy icon. Rows are divided: label + description on the left, the value (sans, `tabular-nums`; unset values get a dashed "Not set" outline) with its updated date, and an Edit button on the right that opens `edit-setting-dialog.tsx` (mounted only while open, seeded with the current value, Save disabled until the value changes) → `PATCH /motel/settings/{key}` with `{ value }` (`updateSetting` in `lib/api/settings.ts`), then invalidates `settingsQueryKey`. The input and validation follow `getSettingInputKind(key)` in `lib/schemas/settings.ts` (`makeSettingSchema(key)` / `toSettingPayload`): `_time` → native time input, 24h `HH:MM`; `_percentage` → whole number 0–100; `_hours` / `_minutes` / `_attempts` → whole number > 0 (unit shown beside the input, `getSettingUnit`); `catering_email` (`EMAIL_LIST_KEYS`) → comma-separated emails, sent without spaces; other `_email` → one email; `mpesa_paybill` (`DIGIT_KEYS`) → digits only; anything else → free text. Every value is sent as a string. Labels come from `getSettingLabel` in `lib/settings.ts` (a key → label map kept close to the key, e.g. `bb_cutoff_time` → "Bed and breakfast cutoff time"; unknown keys fall back to `humanizeSlug`), values from `formatSettingValue` (unit from the key suffix: `_percentage` → %, `_hours` / `_minutes` / `_attempts` pluralised, `_email` comma lists spaced). Don't reintroduce per-category colours, per-setting cards, coloured left stripes, category pills or monospace values here; add a new key to `SETTING_CATEGORY` (and `SETTING_LABELS`) instead.
- `@tanstack/react-query` `react-hot-toast` is mounted once via `components/app-toaster.tsx` in the root layout; call `toast.success(...)` etc. from anywhere.

### Forms

Pattern used by every auth form: `react-hook-form` + `zodResolver` with schemas in `lib/schemas/auth.ts` (zod v4 — note `z.email()` is top-level, not `z.string().email()`). Types are inferred from schemas (`LoginValues`, etc.). Forms wrap fields in `<fieldset disabled={isSubmitting}>`, surface server errors via `setError("root", ...)`, and use the `AuthField`/`AuthInput`/`AuthLabel` wrappers from `components/auth/auth-field.tsx`, which handle label, error text, and `aria-describedby` ids (`${htmlFor}-error`).

### Styling

- `cn` is the **`cn` npm package**, re-exported from `lib/utils.ts` — not clsx + tailwind-merge. Existing files import it from either `"cn"` or `"@/lib/utils"`.
- Theme tokens live in `app/globals.css`: shadcn oklch variables (`:root` / `.dark`) plus custom hex tokens registered in `@theme inline` as Tailwind colors. Brand colors are `brand-navy`, `brand-azure`, `brand-teal`; neutrals include `porcelain`, `canvas`, `iron`. Use these utility names (e.g. `bg-brand-azure`, `text-iron`) instead of hardcoding hex values.
- **Role colours** live in `lib/roles.ts`: `super_admin` crimson (rose), `admin` flame (orange), `receptionist` brand blue, `finance` green (emerald), `housekeeping` violet, `catering` amber; `toneByRole` is a `Record<RoleName, …>` so a new role must be given a tone, and unknown slugs fall back to brand blue. Never pick a role colour inline; render roles with `components/role-badge.tsx` (`<RoleBadge role={slug} label?>`), tint avatars with `getRoleClasses(slug).avatar`, and pass `role` to `StatCard` for a coloured title. `getRoleTone` accepts a slug or a label.
- Font utilities: `font-sans`, `font-heading`, `font-ibm-plex`, `font-mono`.
- Dark mode uses the `.dark` class via `@custom-variant dark`.
