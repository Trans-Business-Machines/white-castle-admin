# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Staff admin dashboard for White Castle Motel (Eldoret). Next.js 16 App Router, React 19, TypeScript (strict), Tailwind CSS v4, shadcn/ui (`radix-vega` style, `radix-ui` package). No backend exists yet — auth and data are mocked in-app.

## Next.js version warning

This is **Next.js 16**, which has breaking changes from earlier versions (see [AGENTS.md](AGENTS.md)). Before writing framework-facing code (routing, caching, data fetching, proxy/middleware, metadata), read the relevant guide under `node_modules/next/dist/docs/01-app/` rather than relying on prior knowledge.

## Architecture

### Route groups

- `app/(auth)/` — public screens: `/login`, `/forgot-password`, `/reset-password`, plus `/change-password` (authenticated, not public: the forced new-password screen for accounts flagged `must_change_password`). Its layout renders the branded split panel (gradient aside + centered form column). Pages are thin: they set `metadata.title` and compose `AuthPanel` + a form component.
- `app/(dashboard)/` — authenticated area: `/dashboard`, `/bookings`, `/guests`, `/units`, `/requests`, `/reports`, `/users`, `/profile`. Most pages are stubs; `/profile` renders `components/profile/profile-view.tsx` (account details, change-password dialog, sign out).
- `app/page.tsx` redirects `/` → `/login`.
- `app/layout.tsx` is the root: loads fonts (Inter → `--font-sans`, Manrope → `--font-heading`, IBM Plex Sans → `--font-ibm-plex`, Geist Mono → `--font-mono`) and wraps everything in `ThemeProvider` (next-themes, class strategy) → `AuthProvider` → `TooltipProvider`.

### Auth

The backend is a FastAPI-style API (errors come back as `{ detail: string | ValidationError[] }`; use `getApiErrorMessage` from `lib/api/errors.ts`).

- **The browser never calls the backend origin directly.** `next.config.ts` rewrites `/api/:path*` to `API_PROXY_TARGET` (server-only env), and `NEXT_PUBLIC_API_BASE` is `/api`. This keeps the refresh cookie same-site: the backend sets it `SameSite=Lax` without `Secure`, so a cross-site call from `localhost` would never store or send it and every reload would land on `/login`. See `.env.example`. Restart `npm run dev` after editing `.env`.

- **Token model:** the access token lives only in memory (`lib/auth-token.ts`); the refresh token is an HTTP-only cookie set by the server. Nothing auth-related is written to localStorage.
- `lib/axios.ts` exports `axiosInstance` (baseURL + `withCredentials`). Its request interceptor injects `Authorization: Bearer`, and its response interceptor refreshes once on a 401 (`POST /auth/refresh`, deduped across concurrent failures) and replays the request. If the refresh fails it fires `onUnauthorized` listeners. Use this instance for every authenticated call.
- `lib/api/auth.ts` wraps the auth endpoints. `login`, `requestPasswordReset` (`/auth/password-reset`), and `confirmPasswordReset` (`/auth/password-reset/confirm`) use bare `axios` so interceptors never touch them; `fetchMe` (`/auth/me`), `logout`, and `changePassword` (`PATCH /auth/change-password`) use `axiosInstance`.
- `providers/auth-provider.tsx` exposes `useAuth()` (`user`, `accessToken`, `status`, `isLoggedIn`, `login`, `logout`, `refreshUser`). On mount it refreshes, fetches `/auth/me`, then routes: signed-in visitors on `/` or a public auth route go to `/dashboard`; failures on a protected route go to `/login`. While that runs it renders `WorkspaceLoader` instead of the app. `isPublicRoute()` is the single source of truth for public paths.
- `components/auth/require-auth.tsx` wraps the `(dashboard)` layout and bounces unauthenticated users to `/login`, and users with `must_change_password` to `/change-password`.
- **Temporary passwords.** `getLandingPath(user)` (in the provider) returns `/change-password` when `must_change_password` is true, else `/dashboard`; the login form, the bootstrap redirect and `RequireAuth` all use it so a reload cannot skip the step. `components/auth/forced-change-password-form.tsx` calls the same `changePassword` endpoint as the profile dialog, then `refreshUser()` (re-fetches `/auth/me`) and routes to the dashboard. The three password inputs are shared via `components/auth/change-password-fields.tsx`.
- Two account menus share one popover pattern: `components/dashboard/sidebar-user.tsx` (sidebar footer, name + role, gradient popover) and `components/dashboard/header-user.tsx` (header, name + email, porcelain popover, avatar-only under `sm`). Both use the `useLogout()` hook (`hooks/use-logout.ts`) and `getInitials()` from `lib/format.ts`; reuse those rather than re-implementing sign-out or initials.
- **Server state: always `@tanstack/react-query` + `axiosInstance`.** Never call `axios`/`fetch` directly from a component. API helpers live in `lib/api/*` (one file per resource: `roles.ts` and `users.ts` each export `fetch*`, `create*`, and a `*QueryKey`). Reads use `useQuery` with that key (gate with `enabled` when the data is only needed inside a dialog). Mutations use `useMutation` inside the component, invalidate the resource's query key on success, show a `toast.success`, and surface failures via `setError("root", …)`. See `components/users/add-role-dialog.tsx` (simplest) and `components/users/create-user-dialog.tsx` (adds a `useQuery`-fed shadcn `Select` via `Controller`, and a generated temporary password from `lib/password.ts` that always satisfies `passwordSchema`; `must_change_password` is hard-coded `true` in `toCreateUserPayload`). Tables: `components/users/users-table.tsx` and `roles-table.tsx` are `useQuery`-backed with client-side search (`SearchInput` in `table-toolbar.tsx`); loading/empty/error rows come from `table-state.tsx`. The users table resolves role slugs to labels via the roles query (`humanizeSlug` fallback). Row actions live in `user-actions-menu.tsx`: a shadcn `DropdownMenu` (enable / disable / delete, delete is `variant="destructive"`) where each item opens the generic `components/confirm-dialog.tsx` and runs one `useMutation`; the signed-in user cannot disable or delete themselves. Endpoints: `POST /auth/users/{id}/enable`, `POST /auth/users/{id}/disable`, `DELETE /auth/users/{id}`. `role-actions-menu.tsx` is the same pattern for the roles table with a single Delete role item (`DELETE /auth/roles/{name}` via `deleteRole`); it invalidates both `rolesQueryKey` and `usersQueryKey` since the users table resolves labels from roles. Roles: the user types one name; `toRolePayload` in `lib/schemas/roles.ts` derives `name` (lowercase snake_case slug, matching existing `super_admin`) and `label` (first letter capitalised).
- **Units** (`/units`): `components/units/unit-stats-card.tsx` renders `UnitStatsCards` (`GET /bookings/rooms/stats`, one `StatCard` per `UnitStatKey`; card copy/tones come from `UNIT_STAT_CARDS` in `lib/units.ts`; `other` is deliberately excluded). `components/units/units-table.tsx` searches by room number/type/status; its last column is `unit-actions-menu.tsx` (View → `/units/[id]`, Update → `edit-unit-dialog.tsx`, Delete). Rows prefetch the room's details query (`queryClient.query(...).catch(noop)` — `prefetchQuery` is deprecated in react-query 5.103 — with a 30s `staleTime`) and route on hover/focus so View/Update open instantly. `/units/[id]` (`params` is a Promise in Next 16) renders `components/units/unit-details.tsx`, which queries `fetchUnitDetails` under `unitQueryKey(roomId)` and has Update/Delete CTAs top-right. Deletion is centralised in `components/units/delete-unit-dialog.tsx` (`DELETE /bookings/rooms/{id}` via `deleteUnit`, confirm dialog, then invalidates `unitsQueryKey`; the details page passes `onDeleted` to go back to `/units`). Query keys are prefixed (`["units"]`, `["units","stats"]`, `["units", id]`) so invalidating `unitsQueryKey` refreshes all three. Status pills come from `components/units/unit-status-badge.tsx` with tones in `lib/units.ts` (`getUnitStatusClasses`, unknown statuses go neutral; `getRoomTypeLabel` maps `ROOM_TYPES` slugs). The form inputs (details, amenity chips, photo picker) live in `components/units/unit-form-fields.tsx` and are shared by the add and edit dialogs, which own the `useForm` + `useMutation`. `edit-unit-dialog.tsx` is controlled (`open`/`onOpenChange`) and mounts its form only while open so each open re-seeds from the room; it does `updateUnit` (`PATCH /bookings/rooms/{id}`, full `toUnitPayload` body) then the optional photo upload with the same retry-photo-only behaviour, and the dropzone starts empty (existing photos are kept). `components/units/add-unit-dialog.tsx` follows the same dialog pattern but saves in two steps because photos hang off an existing room: `createUnit` (`POST /bookings/rooms`, body from `toUnitPayload` in `lib/schemas/units.ts`) then `uploadUnitPhoto` (`POST /media/upload/room-photo/{room_id}`, multipart field `file`). If the upload fails the dialog keeps the created room in `savedUnit`, locks the detail fields and resubmitting only retries the photo. Amenities are typed one at a time into a chip list (`amenitySchema` validates each). `components/units/photo-dropzone.tsx` is the single-image drag-and-drop picker with preview; the accepted types/size (`ROOM_PHOTO_TYPES`, `ROOM_PHOTO_MAX_BYTES`, `getRoomPhotoError`) live in the schema file so the picker and zod can't disagree.
- **Guests** (`/guests`): mirrors the Units structure. `components/guests/guest-stats-cards.tsx` renders `GuestStatsCards` (`GET /guests/stats` under `guestStatsQueryKey`, one `StatCard` per `GuestsStats` key; copy/tones come from `GUEST_STAT_CARDS` in `lib/guests.ts`). `guests-table.tsx` (Name w/ initials + blacklist badge, Phone, Email, Nationality, ID number + type, Actions; search by name/phone/email; hover/focus prefetches `guestQueryKey(id)` and the route). `guest-actions-menu.tsx`: View guest → `/guests/[id]`, Update → `edit-guest-dialog.tsx`, then Blacklist guest / Remove from blacklist depending on `guest.blacklisted`. `/guests/[id]` renders `guest-details.tsx` (Contact / Identity / Record cards, Update + Blacklist CTAs; a bookings section is still TODO). Form inputs are shared via `guest-form-fields.tsx`; `toGuestFormValues` in `lib/schemas/guests.ts` pre-fills the edit form (parses `date_of_birth` back to a `Date`). `blacklist-guest-dialog.tsx` branches on `guest.blacklisted`: blacklisting opens a small form asking for a reason (`blacklistSchema` / `toBlacklistPayload` → `PATCH /guests/{id}/blacklist` with `{ reason }`), un-blacklisting is a plain `ConfirmDialog` → `/unblacklist`. The profile shows `total_stays` / `total_spent` as `StatCard`s, the `blacklist_reason` in the banner and `notes` in their own card; `id_documents` is typed but not rendered yet. API helpers in `lib/api/guests.ts`: `fetchGuests`, `fetchGuestDetails`, `createGuest`, `updateGuest` (`PATCH /guests/{id}`), `blacklistGuest`, `unblacklistGuest`; keys `["guests"]` / `["guests", id]`.
- **Bookings** (`/bookings`): `components/bookings/new-booking-dialog.tsx` owns the `useForm` (`bookingSchema` in `lib/schemas/bookings.ts`) and the `createBooking` mutation (`POST /bookings/create`, body typed as `CreateBookingPayload` in `lib/types.ts`). On mount it warms `unitsQueryKey` and `guestsQueryKey` with `queryClient.query(...).catch(noop)` (30s `staleTime`) so the pickers are populated the moment the dialog opens; the `useQuery`s themselves are `enabled: open`. The form stores `room_id` + `guest_id`; `toBookingPayload(values, guest)` copies `guest_name/email/phone` from the chosen `Guest`. Inputs live in `booking-form-fields.tsx`: `room-select.tsx` (shadcn `Select` over every room, non-`available` rooms disabled with the status in brackets, `isRoomBookable`), `guest-combobox.tsx` (Popover + Command, cmdk `keywords` = name/email/phone, blacklisted guests disabled), `stay-date-picker.tsx` (check-out `minDate` is the day after check-in; schema also enforces check-out > check-in and check-in ≥ today), numeric adults/children (`valueAsNumber`, `MAX_OCCUPANTS`) and a special-requests textarea. Success invalidates `bookingsQueryKey` and `unitsQueryKey` (the room's status changes). `booking-stats-cards.tsx` renders `BookingStatsCards` (`GET /bookings/occupancy?from_date&to_date`, month-to-date via `getMonthToDateRange` in `lib/bookings.ts`, key `["bookings","stats",from,to]`); `BOOKING_STAT_CARDS` there carries each card's copy, tone and `format` (revenue → `formatCurrency`, rate → `formatPercent`); `currently_occupied` is deliberately excluded from `BookingStatKey`. `bookings-table.tsx` lists `GET /bookings/list` under `bookingsListQueryKey(filters)` (`["bookings","list",{status,date_from,date_to}]`, empty filters omitted from the query string, `placeholderData: keepPreviousData` so filter changes dim the old rows instead of showing a skeleton). Filters live in `bookings-filters.tsx` (status `Select` over `BOOKING_STATUSES` with an `all` sentinel, two `StayDatePicker`s for the date range, Clear filters). The `SearchInput` above them is a reference lookup: the debounced (`hooks/use-debounced-value.ts`), upper-cased term hits `GET /bookings/lookup/{reference}` under `bookingLookupQueryKey`, the list query is disabled and the filters greyed out while it's active, and a 404 renders "No booking with reference …" (not retried). `Booking` (`lib/types.ts`) carries only `room_id`, so the table resolves room numbers from the units query (`—` when unknown); `reference` is the display ref and `total_amount` the cost. Status / payment pills are `booking-status-badge.tsx` with tones from `getBookingStatusClasses` / `getPaymentStatusClasses` in `lib/bookings.ts`. `booking-actions-menu.tsx` starts with View booking → `/bookings/[id]` (`getBookingHref`; `showView={false}` hides it on the details page), then Approve / Confirm payment / Check in / Check out / Reject / Cancel items that are **not wired yet** (`handleAction` is a no-op). Rows prefetch `bookingQueryKey(id)` (`GET /bookings/{id}` via `fetchBookingDetails`) and the route on hover/focus. `/bookings/[id]` renders `booking-details.tsx`: reference + status/payment pills + actions menu, a rejected/cancelled banner with the reason, `StatCard`s (total, deposit, nights, guests), Stay (room resolved from the units query and linked to `/units/[id]`), Guest (linked to `/guests/[id]` when `guest_id` is set), Payment, Timeline (created/approved/checked in/out/cancelled with `formatTimestamp` from `lib/format.ts`) and the `qr_code` data URI. `guest_id` filtering is not exposed yet.
- `@tanstack/react-query` `react-hot-toast` is mounted once via `components/app-toaster.tsx` in the root layout; call `toast.success(...)` etc. from anywhere.

### Forms

Pattern used by every auth form: `react-hook-form` + `zodResolver` with schemas in `lib/schemas/auth.ts` (zod v4 — note `z.email()` is top-level, not `z.string().email()`). Types are inferred from schemas (`LoginValues`, etc.). Forms wrap fields in `<fieldset disabled={isSubmitting}>`, surface server errors via `setError("root", ...)`, and use the `AuthField`/`AuthInput`/`AuthLabel` wrappers from `components/auth/auth-field.tsx`, which handle label, error text, and `aria-describedby` ids (`${htmlFor}-error`).

### Styling

- `cn` is the **`cn` npm package**, re-exported from `lib/utils.ts` — not clsx + tailwind-merge. Existing files import it from either `"cn"` or `"@/lib/utils"`.
- Theme tokens live in `app/globals.css`: shadcn oklch variables (`:root` / `.dark`) plus custom hex tokens registered in `@theme inline` as Tailwind colors. Brand colors are `brand-navy`, `brand-azure`, `brand-teal`; neutrals include `porcelain`, `canvas`, `iron`. Use these utility names (e.g. `bg-brand-azure`, `text-iron`) instead of hardcoding hex values.
- **Role colours** live in `lib/roles.ts`: `super_admin` crimson (rose), `admin` flame (orange), `finance` green (emerald), `housekeeping` violet, everything else brand blue. Never pick a role colour inline; render roles with `components/role-badge.tsx` (`<RoleBadge role={slug} label?>`), tint avatars with `getRoleClasses(slug).avatar`, and pass `role` to `StatCard` for a coloured title. `getRoleTone` accepts a slug or a label.
- Font utilities: `font-sans`, `font-heading`, `font-ibm-plex`, `font-mono`.
- Dark mode uses the `.dark` class via `@custom-variant dark`.
